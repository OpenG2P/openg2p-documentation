# Standards

Open Agri Stack is built from many OpenG2P components. This page lists, area by area, which open standard each part follows, which components use it, and where no standard is followed.

**Components:** **RP** Registry Platform, and the registries built on it: **FR** Farmer Registry, **CSR** Crop Sown Registry. **Composite** the use-case composite (partner entry point). **CM** Consent Manager. **PM** Partner Management. **MDS** Master Data Service (the catalogue). **AWE** Approval Workflow Engine. Plus Keycloak, the Audit Manager, Inji Certify, ODK Central and the cluster's Istio / Nginx.

| Status | Meaning |
| --- | --- |
| **Used** | The standard is followed. |
| **Partly** | Followed in large part, adapted, or used as a mapping or inspiration. |
| **Own** | Our own format; no standard is applied. |
| **To explore** | A standard exists that should be evaluated for adoption. |

{% hint style="info" %}
Standards for consent itself (consent receipts, data-subject rights, artefact semantics) are covered on the Consent Manager's [standards and best practices](../../consent-management/design/standards-and-best-practices.md) page and summarised here.
{% endhint %}

## Data exchange between systems

| Area | Components | Where | Standard | Status | Notes |
| --- | --- | --- | --- | --- | --- |
| Registry search API | RP (FR, CSR), Composite | FR and CSR partner APIs; the composite calling them | [DCI](https://standards.spdci.org/) (Digital Convergence Initiative) registry API: signed envelope, `sync/search`, `idtype-value` and `expression` queries | **Used** | Only the synchronous search is offered; DCI's asynchronous search and subscribe/notify are not (subscribe/notify is a [TODO](../open-items/README.md)). Filters on activity registers (`subject_id`, crop year, season) are our use of DCI's `expression` query. |
| Farmer record | RP (FR) | FR's DCI record (`spdci-extensions-dci:Farmer`) | DCI / SPDCI farmer data model | **Partly** | Follows most of the DCI farmer model (personal details, identifiers, family, farm details). DCI defines more detail than is practical to fill; adds `FARMER_ID` beside the Fayda UIN and declared `main_crops`. |
| Crop activity, crop season and season-summary records | RP (CSR) | CSR's DCI records (`spdci-extensions-agri:CropActivity`, `…:CropSeason`, `…:ActivityAggregate`) | — | **Own** | Our own record types under an `spdci-extensions-agri` name; not a published DCI extension. To explore: proposing them as a DCI agriculture extension. |
| Composite partner API | Composite | `POST /composite/v1/use-cases/{use_case}/query` | Modelled on the DCI envelope (signed `header` + `message`) | **Own** | The body (subject, parameters, consent) and the response's `data` (shaped per use case) are our own. Publishing a JSON Schema / OpenAPI per use case is a [TODO](../open-items/README.md). |
| Data publishing to subscribers | RP (FR, CSR), WebSub hub | Registry outgestion (register records and activity events) | [W3C WebSub](https://www.w3.org/TR/websub/) | **Used** | The registry platform registers topics with a WebSub hub and publishes changes to subscribers. |
| API descriptions | All services | Every service | [OpenAPI 3](https://spec.openapis.org/oas/latest.html) | **Used** | Generated by FastAPI. |
| Payload validation | RP (CSR activity types), Composite (use cases), MDS (list attribute schemas) | Activity types' payloads; use-case files | [JSON Schema](https://json-schema.org/) | **Used** | Each activity type's payload is a JSON Schema; schema versions are kept per type. |
| Field capture | RP (CSR), ODK Central | Crop sowing form | [ODK XForms](https://getodk.github.io/xforms-spec/) via ODK Central | **Used** | |
| Network discovery | OAN network layer (not an OpenG2P component) | OAN network layer | [Beckn](https://becknprotocol.io/) | **Used** (outside the registries) | Only for discovering service providers and consumers; never for registry data. |

## Security, identity and trust

| Area | Components | Where | Standard | Status | Notes |
| --- | --- | --- | --- | --- | --- |
| Request signatures | Partners, Composite, RP (FR, CSR partner APIs), PM (keys) | Partner → composite → registries; responses | JWS ([RFC 7515](https://www.rfc-editor.org/rfc/rfc7515)), detached, over `{header, message}` | **Used** | Algorithms EdDSA ([RFC 8037](https://www.rfc-editor.org/rfc/rfc8037)), ES256 and RS256 ([RFC 7518](https://www.rfc-editor.org/rfc/rfc7518)); `none` and HS* refused. |
| Public keys | PM, CM | Partner Management | JWK / JWKS ([RFC 7517](https://www.rfc-editor.org/rfc/rfc7517)); SPKI PEM | **Used** | CM publishes its receipt-signing key at `/.well-known/jwks.json`. |
| Service keystores | Composite, CM | The composite's and CM's signing keys | PKCS#12 | **Used** | |
| Staff and service authentication | Keycloak; RP, PM, CM, MDS, AWE, Composite | Keycloak | OAuth 2.0, OpenID Connect | **Used** | Client credentials for service-to-service admin calls. |
| Transport | Istio (cluster) | Cluster | TLS; mutual TLS inside the mesh (Istio) | **Used** | |
| National identity | RP (FR), Composite, CM | Farmer subject | Fayda (Ethiopia's national ID, built on MOSIP) FAN | **Used** | The FR farmer ID (`FR-…`) is our own identifier, linked to the FAN. |
| Certificates | RP (agent portal), Inji Certify | VC issuance (agent portal, Inji Certify) | [W3C Verifiable Credentials](https://www.w3.org/TR/vc-data-model-2.0/), [OpenID4VCI](https://openid.net/specs/openid-4-verifiable-credential-issuance-1_0.html) | **Used** | See [VC issuance](../../platform/platform-services/vc-issuance/README.md). |
| Credential status | Inji Certify, RP | Revoking a credential when its record changes | [W3C Bitstring Status List](https://www.w3.org/TR/vc-bitstring-status-list/) | **Partly** | Certify keeps a status list; using it when the source record is changed or corrected is an [open item](../open-items/README.md). |

## Consent and data-share policy

| Area | Components | Where | Standard | Status | Notes |
| --- | --- | --- | --- | --- | --- |
| Consent object | Partners, Composite, CM, RP | Partner → registries, validated by CM | JWT ([RFC 7519](https://www.rfc-editor.org/rfc/rfc7519)) signed as JWS; JSON-LD `@context` | **Partly** | The claims (`subject_id`, `purpose`, `grants`, `validity`, `jti`, …) and the JSON-LD vocabulary are OpenG2P's own. |
| Consent records and receipts | CM | CM | Kantara Consent Receipt 1.1; ISO/IEC 29184 and ISO/IEC TS 27560 | **Used** | Signed receipts per consent and registry. See [CM standards](../../consent-management/design/standards-and-best-practices.md). |
| Consent artefact semantics | CM | CM | DEPA / Account Aggregator (granular, revocable, time-bound, fetch semantics) | **Used** | |
| Data-subject rights | CM | CM | GDPR principles (purpose limitation, minimisation, access, withdrawal) | **Used** | |
| Purposes | CM, Composite | CM policies, use cases | [W3C DPV](https://w3c.github.io/dpv/) (Data Privacy Vocabulary) | **To explore** | Purpose codes (e.g. `credit-assessment`) are our own. |
| Data-share policies | CM (PM later) | CM today, PM later | [W3C ODRL](https://www.w3.org/TR/odrl-model/) | **To explore** | Policies are our own model (allowed scopes, purposes, subject ID types, validity). |
| Consent decision | CM (decision point), RP (enforcement point) | Registry ↔ CM | PDP / PEP pattern (XACML terminology) | **Partly** | The roles follow the pattern; the `/validate` API is our own. |
| Consent scopes | RP (scope catalogue, enforcement), CM, Composite | Each registry's [data scope catalogue](../../products/registry/registry/design/data-scopes.md) | — | **Own** | Scopes are named, versioned groups of a registry's own fields, independent of DCI or any other output format. To explore: DPV personal data categories. |

## Catalogues and reference data

| Area | Components | Where | Standard | Status | Notes |
| --- | --- | --- | --- | --- | --- |
| Code lists | MDS, RP | [Catalogues](../architecture/registry-model.md#layer-2-catalogues) (MDS for now) | — | **Own** | Codes are the country's (e.g. `CROP_TEFF`, `SEASON_MEHER`). To explore: publishing them as [W3C SKOS](https://www.w3.org/TR/skos-reference/) (JSON-LD). |
| Crop and commodity codes | MDS | `CROP_COMMODITY` | FAO [AGROVOC](https://agrovoc.fao.org/), FAO Indicative Crop Classification, FAOSTAT commodity codes | **To explore** | As optional mappings from the country's codes. |
| Administrative areas | MDS, RP | Catalogues; every activity's location | OCHA COD-AB P-codes (e.g. `ET040611`) | **Used** | The Ethiopia country pack's geography; CC BY-IGO licence (see [Country Data Architecture](../../platform/country-data-architecture.md)). |
| Shapes | RP (FR), MDS (boundaries in the object store) | FR land parcels; catalogue boundaries | GeoJSON ([RFC 7946](https://www.rfc-editor.org/rfc/rfc7946)) | **Used** | To explore: publishing boundaries through [OGC API – Features](https://ogcapi.ogc.org/features/). |
| Dataset descriptions | MDS, RP, Composite | Catalogues, use cases | [W3C DCAT](https://www.w3.org/TR/vocab-dcat-3/) | **To explore** | For describing what each registry and use case offers. |

## Own formats and standards to explore

In one place, what is our own today and what to evaluate:

* **Own, with a candidate standard:**
  * crop activity, crop season and summary records: propose as a DCI agriculture extension;
  * code lists: publish as SKOS; map crop codes to AGROVOC / FAO classifications;
  * purposes and policies: DPV and ODRL;
  * units: UCUM.
* **Own, by design:**
  * the composite's partner API body and response (a JSON Schema per use case is still to be published);
  * the consent object's claims and the CM `/validate` API;
  * the Ethiopian calendar conversion.
* **To explore, not yet used:** OGC API – Features for boundaries, DCAT for dataset descriptions, ISO 19156 / SensorThings / PROV for observations, W3C Trace Context and OpenTelemetry for tracing, Bitstring Status List for credentials after a record change.
