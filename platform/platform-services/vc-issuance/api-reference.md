# API Reference

All paths below are relative to the Certify service path `…/v1/certify`. Examples use the
`ldp_vc` (JSON-LD) format and the values observed in the [verified local trial](local-setup.md).

## Part A — Inji Certify endpoints

### Discovery

| Method | Path | Purpose |
|---|---|---|
| GET | `/.well-known/openid-credential-issuer` | Issuer + credential metadata (used by wallets) |
| GET | `/.well-known/oauth-authorization-server` | OAuth metadata (Certify acting as its own AS) |
| GET | `/.well-known/jwks.json` | Public signing keys |
| GET | `/.well-known/did.json` | Issuer DID document |

### Credential offer (pre-authorized code) — called by the source application

**`POST /pre-authorized-data`** — the source app pushes claims + a PIN; gets back an offer URI.

```jsonc
// request
{
  "credential_configuration_id": "FarmerCredential",
  "claims": { "fullName": "Jane Thompson", "dateOfBirth": "1998-01-24", "gender": "Female" },
  "expires_in": 600,
  "tx_code": "53192"           // the PIN, generated by the portal
}
// response
{ "credential_offer_uri": "openid-credential-offer://?credential_offer_uri=https://<certify>/v1/certify/credential-offer-data/<offer_id>" }
```

> The allowed `claims` keys are exactly the credential's configured `credential_subject` keys.
> Unknown keys are rejected; template fields not supplied render empty.

**`GET /credential-offer-data/{offer_id}`** — fetched by the wallet; returns the offer with the
`pre-authorized_code` and the `tx_code` descriptor.

### Token + credential — called by the wallet

**`POST /oauth/token`** (`application/x-www-form-urlencoded`)

```
grant_type=urn:ietf:params:oauth:grant-type:pre-authorized_code
&pre-authorized_code=<from offer>
&tx_code=53192
→ { "access_token": "...", "c_nonce": "...", "token_type": "Bearer", "expires_in": ... }
```

**`POST /issuance/credential`** (`Authorization: Bearer <access_token>`)

```jsonc
{
  "format": "ldp_vc",
  "credential_definition": {
    "@context": ["https://www.w3.org/2018/credentials/v1"],
    "type": ["VerifiableCredential", "FarmerCredential"]
  },
  "proof": { "proof_type": "jwt", "jwt": "<openid4vci-proof+jwt signed by the wallet's key>" }
}
→ { "credential": { ... signed VC ... } }
```

The proof JWT header is `{ "alg": "...", "typ": "openid4vci-proof+jwt", "jwk": <holder pubkey> }`
and the payload carries `{ "aud": "<credential issuer>", "nonce": "<c_nonce>", "iss": "" }`. The
holder's key becomes the credential subject `id` (a `did:jwk`).

### Credential configuration (issuer onboarding) — admin

**`POST /credential-configurations`** — defines a credential type: its template, format, issuer
DID and signing key.

```jsonc
{
  "credentialConfigKeyId": "FarmerCredential",
  "credentialFormat": "ldp_vc",
  "credentialTypes": ["VerifiableCredential", "FarmerCredential"],
  "contextURLs": ["https://www.w3.org/2018/credentials/v1"],
  "didUrl": "did:web:<issuer-host>",          // issuing authority / sub-department DID
  "keyManagerAppId": "CERTIFY_VC_SIGN_ED25519", // which signing key
  "keyManagerRefId": "ED25519_SIGN",
  "signatureAlgo": "EdDSA",
  "signatureCryptoSuite": "Ed25519Signature2020",
  "vcTemplate": "<base64 Velocity template>",
  "metaDataDisplay": [ /* logos, colors, labels */ ]
}
```

`GET|PUT|DELETE /credential-configurations/{credentialConfigKeyId}` manage existing configs.

## Part B — Proposed Beneficiary Portal (Registry/PBMS) VC APIs

These are **new** endpoints to add to `registry-bene-portal-api` (and the equivalent in PBMS),
written fresh for Inji Certify integration. They follow the existing OpenG2P FastAPI
conventions (`G2PRequest`/`G2PResponse` envelopes, auth via the shared IAM library). Shapes
below are indicative and to be finalized during implementation.

### List credentials available to the citizen

`POST /beneficiary_portal/credentials/list` → the credential types this citizen is eligible to
download (driven by registry/PBMS data + configured credential types).

```jsonc
// response payload
[ { "credential_type": "FarmerCredential", "title": "Farmer Identity Card", "available": true } ]
```

### Create a credential offer (the "Download Credential" action)

`POST /beneficiary_portal/credentials/offer`

```jsonc
// request payload
{ "credential_type": "FarmerCredential" }

// server side: resolve citizen from IAM token → fetch record → build claims →
// generate PIN → call Certify POST /pre-authorized-data → return:

// response payload
{
  "credential_offer_uri": "openid-credential-offer://?credential_offer_uri=...",
  "pin": "53192",
  "expires_in": 600
}
```

The UI renders `credential_offer_uri` as a **QR** and shows the **PIN**. The portal never
returns or stores the signed VC — the wallet fetches it from Certify directly.

### (Optional) Offer status

`POST /beneficiary_portal/credentials/status` → whether an offer was redeemed (for UI feedback),
if status tracking is enabled.

## Notes

* The portal authenticates to Certify's `/pre-authorized-data` as a **trusted M2M client**; do
  not expose that endpoint publicly.
* The mapping from the IAM token subject to the citizen's registry/PBMS record (the
  *identity-linkage* resolver) is an implementation detail to be defined per source app.
