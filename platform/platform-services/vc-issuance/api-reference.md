# API Reference

Three API surfaces matter: **Mimoto** (hosted wallet), **Inji Certify** (issuer), and the
**Registry REST API** that Certify's connector calls. Shapes are indicative and to be finalized
against the pinned versions (Certify 0.14.0, Mimoto 0.22.0) during implementation.

## Mimoto — hosted wallet (called by branded Inji Web)

| Method | Path | Purpose |
|---|---|---|
| POST | `/wallets` | Create the citizen's hosted wallet (PIN) |
| POST | `/wallets/{walletId}/unlock` | Unlock the wallet |
| POST | `/wallets/{walletId}/credentials` | **Download + store** a VC from an issuer |
| GET | `/wallets/{walletId}/credentials` | List stored credentials |
| GET | `/wallets/{walletId}/credentials/{credentialId}` | Get a credential — **as PDF** (`Accept: application/pdf`) |
| DELETE | `/wallets/{walletId}/credentials/{credentialId}` | Delete |
| POST | `/wallets/{walletId}/presentations` | Present (OpenID4VP) — *later scenario* |

### Download a credential into the wallet (the deposit)

`POST /wallets/{walletId}/credentials` — **authorization_code + PKCE** (this is the only ingest path):

```jsonc
{
  "issuer": "<Certify issuer id from mimoto-issuers-config.json>",
  "credentialConfigurationId": "RegistryCredential",
  "code": "<auth code from Logto>",
  "grantType": "authorization_code",
  "redirectUri": "https://wallet.dept.gov/callback",
  "codeVerifier": "<PKCE verifier generated by Inji Web>"
}
```

Mimoto exchanges the code with Logto, calls Certify's credential endpoint, then **stores** the
signed VC (`verifiable_credentials` table) and returns its metadata.

### Download the PDF

`GET /wallets/{walletId}/credentials/{credentialId}` with `Accept: application/pdf` → the
rendered PDF (may embed a QR for offline verification).

## Inji Certify — issuer

| Method | Path | Purpose |
|---|---|---|
| GET | `/.well-known/openid-credential-issuer` | Issuer/credential metadata (used by Mimoto) |
| GET | `/.well-known/jwks.json` | Public signing keys |
| GET | `/.well-known/did.json` | Issuer DID document |
| POST | `/issuance/credential` | Credential endpoint (called by Mimoto with the Bearer token) |
| POST/GET/PUT/DELETE | `/credential-configurations[/{id}]` | Manage credential types (admin) |

### Define a credential type (admin)

`POST /credential-configurations` — issuer DID + signing key + template per credential type:

```jsonc
{
  "credentialConfigKeyId": "RegistryCredential",
  "credentialFormat": "ldp_vc",
  "credentialTypes": ["VerifiableCredential", "RegistryCredential"],
  "contextURLs": ["https://www.w3.org/2018/credentials/v1"],
  "didUrl": "did:web:<issuer-host>",
  "keyManagerAppId": "CERTIFY_VC_SIGN_ED25519",
  "keyManagerRefId": "ED25519_SIGN",
  "signatureAlgo": "EdDSA",
  "signatureCryptoSuite": "Ed25519Signature2020",
  "vcTemplate": "<base64 Velocity template>"
}
```

Certify is configured to trust **Logto** as the token issuer
(`mosip.certify.authn.issuer-uri` / `jwk-set-uri`), and to use the **Registry connector** plugin
(`mosip.certify.integration.data-provider-plugin`).

## Registry data connector — Phase 1 (DB-direct, Postgres plugin)

Phase 1 uses the stock **`PostgresDataProviderPlugin`** (no custom code). The "contract" is a
SQL query + a view, not a REST call. Full design: [Registry Data Connector](registry-data-connector.md).

* **Plugin selection:** `mosip.certify.integration.data-provider-plugin=PostgresDataProviderPlugin`.
* **Scope → query mapping** (the `:id` parameter is bound to the token **`sub`**):
  ```properties
  mosip.certify.data-provider-plugin.postgres.scope-query-mapping={\
    'registry_vc_ldp': 'select full_name, date_of_birth, gender, functional_id \
                         from certify.beneficiary_vc_view where phone = :id'\
  }
  ```
* **The view** `certify.beneficiary_vc_view` exposes only VC-relevant columns, keyed by **phone**,
  **active-only**, surfaced inside Certify's DB via FDW / sync / cross-schema.
* **Returned columns → VC claims:** column names align with the credential's `credential_subject`
  keys / template `${...}`. The **functional ID** is a claim; holder binding
  (`credentialSubject.id`) is the hosted wallet's custodial key.
* **Behaviours:** 1 active row → issued; no row (absent **or** inactive) → plugin *No Data Found* →
  Certify error → portal shows "no eligible record".
* **Requirement:** the token **`sub` must be the phone number** (Logto config), since the plugin
  keys `:id` on `sub`.

### Phase 2 (alternative) — custom REST connector

A custom `DataProviderPlugin` that calls the **Registry REST API**, reads the `phone_number`
claim, and returns a JSON claims object — avoiding the DB coupling and the `sub`=phone constraint,
at the cost of custom Java. Indicative shape:
```
GET /registry/records?phone={phone}&register={registerId}   (service-auth)
→ { "functionalId": "...", "fullName": "...", "dateOfBirth": "...", ... }
```

## Notes

* The `/wallets/.../presentations` (OpenID4VP) and device-wallet QR offer APIs belong to **later
  scenarios** and are out of scope for Phase 1.
