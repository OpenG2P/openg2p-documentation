# High level design

## Overview

OpenG2P Registry includes a purpose-built **Consent Management microservice** that governs all outbound data sharing. The microservice is external to the registry core: the registry delegates all consent decisions to this service rather than interpreting consent semantics internally.

The fundamental enforcement rule is simple: **no outbound data is shared from the registry without a positive consent authorization from the Consent Management service.**

## Consent flow

The end-to-end consent flow proceeds through the following steps:

1. **Generate consent request** -- the system creates a consent request specifying:
   * Who is the **subject** (e.g. a specific farmer).
   * Which **registers** are being shared (e.g. `farmer_register`, `crop_register`).
   * Who is the **audience** (the partner system requesting data).
   * The **duration** of consent validity.
2. **Authenticate the subject** -- the subject authenticates via an OAuth provider using a supported method (biometric, OTP, or other configured mechanism).
3. **Receive ID Token** -- the OAuth provider issues an ID Token upon successful authentication.
4. **Validate token signature and claims** -- the Consent Management service validates the cryptographic signature and the claims within the ID Token.
5. **Store ID Token hash** -- the service computes and stores a hash of the ID Token. The raw ID Token itself is not persisted.
6. **Generate Auth Context** -- the service creates an Auth Context document containing the ID Token hash, the authentication method, and the verified claims.
7. **Generate Consent Artefact** -- the service creates a Consent Artefact containing all consent claims (subject, partner, data scopes, validity) along with the Auth Context.
8. **Generate Consent Receipt** -- the service signs the Consent Artefact with the registry's private key to produce a Consent Receipt. This receipt serves as cryptographic proof of consent for audit and dispute resolution.

## Data structures

The Consent Management service uses JSON-LD structures for all consent-related documents.

### ID Token

The ID Token is received from the identity provider after subject authentication.

```json
{
  "@context": "https://example.org/contexts/id_token.jsonld",
  "@type": "IDToken",
  "iss": "https://idp.example.org",
  "sub": "FARMER_1234",
  "aud": "my.registry.org",
  "amr": ["otp"],
  "iat": 1714555200,
  "exp": 1714558800,
  "auth_time": 1714555190,
  "kid": "key-2025-01",
  "signature": "BASE64URL(JWS_signature)"
}
```

### Auth Context

The Auth Context is generated by the Consent Management service after validating the ID Token.

```json
{
  "@context": "https://example.org/contexts/auth_context.jsonld",
  "@type": "AuthContext",
  "auth_provider": "keycloak",
  "auth_method": "otp",
  "auth_timestamp": "2025-05-01T12:01:22Z",
  "issuer": "https://idp.example.org",
  "subject_id": "FARMER_1234",
  "kid": "key-2025-01",
  "id_token_hash": "sha256:ab349faa12bc908d...",
  "token_validated": true,
  "verified_claims": {
    "iss": "https://idp.example.org",
    "sub": "FARMER_1234",
    "aud": "my.registry.org",
    "amr": ["otp"],
    "iat": 1714555200,
    "exp": 1714558800,
    "auth_time": 1714555190,
    "kid": "key-2025-01"
  }
}
```

### Consent Artefact

The Consent Artefact captures the full consent decision including subject, partner, data scopes, validity, and the Auth Context.

```json
{
  "@context": "https://example.org/contexts/consent_artefact.jsonld",
  "@type": "ConsentArtefact",
  "consent_id": "CONSENT-123456",
  "subject_id": "FARMER_1234",
  "data_controller": "my.registry.org",
  "partner_system": "PARTNER_SYSTEM_A",
  "purpose": {
    "code": "share_farm_profile",
    "text": "Share farmer profile and crop information with Partner System A"
  },
  "data_scopes": [
    "farmer_profile.basic",
    "farmer_profile.crops",
    "farmer_profile.landholdings"
  ],
  "validity": {
    "consent_timestamp": "2025-05-01T12:02:10Z",
    "expiry_timestamp": "2026-05-01T12:02:10Z"
  },
  "auth_context": {
    "...Auth Context as described above..."
  }
}
```

The Consent Artefact is stored and checked against before any data is published to partner systems.

### Consent Receipt

The Consent Receipt is generated at the same time as the Consent Artefact. It contains a hash of the artefact and is signed by the registry's private key, providing cryptographic proof of consent.

```json
{
  "@context": "https://example.org/contexts/consent_receipt.jsonld",
  "@type": "ConsentReceipt",
  "receipt_id": "RECEIPT-998877",
  "issued_at": "2025-05-01T12:02:12Z",
  "issued_by": "my.registry.org",
  "consent_artefact": {
    "@id": "CONSENT-123456",
    "hash": "sha256:7b0a933e7cd398a..."
  },
  "signature": {
    "algorithm": "ed25519",
    "kid": "registry-2025-01",
    "signature_value": "BASE64URL(registry_private_key.sign(consent_artefact_hash))"
  }
}
```
